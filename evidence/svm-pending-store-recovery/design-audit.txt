Approved control flow and necessary details

1. Go exact, scheme.go around 502: assign Get's signature, hit, and err; return nil, err immediately when err != nil; only then consider hit. Propagate the original infrastructure error (including cancellation), consistent with existing batch Get handling and the outer facilitator's generic-error propagation. Do not convert it to duplicate_settlement, transaction_failed, or settlement_pending, and do not expose an untrusted partial signature as a broadcast result. On error, do not Delete/Set pending data, reconcile, acquire/delete the local dedup entry, verify, sign, or send. Since this lookup precedes the local dedup check/defer, it needs no cache cleanup. Existing malformed-payload checks remain before lookup.

2. Go upto, scheme.go around 380: return nil, false, err on Get error before considering ok. BOTH deposit (~472) and claim (~650) must return resp, err on `err != nil || hit`. A helper-only change loses the error. Update the helper comment: only hit=false AND err=nil authorizes fallthrough; hit=true still means reconciliation was attempted. Keep nil-store and clean-miss behavior. Preserve the existing dispatch/amount validation and delegated authentication before lookup; this change does not move or bypass those checks. Raw error propagation here preserves errors.Is and avoids inventing a payment failure reason.

3. TS exact, scheme.ts around 353–365: retain synchronous isDuplicate(txKey) before the first await. Put ONLY `await this.pendingStore.get(txKey)` inside a try/catch, assigning a signature variable for the existing following block. In catch, delete the local settlement cache key only when !isCachedDuplicate, then `throw error` unchanged. This catches both synchronous throws and promise rejections. Do not delete the pending store. Keep store.delete and reconcilePendingSettlement outside this catch: they operate on potentially broadcast transactions and must not accidentally trigger fresh-lookup lock cleanup. Keep lookup before the duplicate response so a valid pending signature can reconcile on a locally duplicate retry, and a lookup failure remains the surfaced error even for a duplicate.

Concurrency assessment and scope
The proposed TS guard preserves another invocation's entry in the relevant case: A synchronously acquires the key, B observes it as duplicate, and B's lookup fails while A is still active. Unconditional deletion would let C enter while A owns the entry. The guard prevents that; moving lookup ahead of acquisition would weaken this protection. Go's error exit occurs before local cache mutation, so it cannot clear an existing owner.

The boolean is an acquisition-time marker, not a generation token. Existing TTL expiry can allow a new owner after a long wait; subsequent cleanup by an old owner can then remove the newer entry. Also, pending Get/Delete is not an atomic distributed reservation. These are existing broader cache/reconciliation limitations, not solved by this repair. Do not describe the patch as comprehensive cross-replica or arbitrarily-long-running lock safety. No cache API/TTL or distributed-lock redesign is needed for this scoped contribution.

Required regression coverage

A. Go exact: table-drive Get results ("", false, sentinel), (validPriorSignature, true, sentinel), and ideally (validPriorSignature, false, sentinel). Assert nil response and errors.Is(err, sentinel), zero verify/simulate/sign/send/confirm, and zero store Set/Delete. The error must win over a valid partial hit. Seed a real entry in a wrapped in-memory store and verify it remains present through the failed lookup; restore reads and reconcile that exact signature with no broadcast. Add fresh-key failed lookup followed by healthy miss/success to prove ordinary retryability. Existing healthy-hit/miss tests remain useful controls. For an already locked pending retry, assert the store error wins over duplicate_settlement and ownership remains intact.

B. Go upto: exercise public Settle through BOTH deposit and claim, not just the shared helper. Use a valid deposit fixture and the existing voucher claim fixture so dispatch/authentication reaches lookup. For each phase, cover miss+error and partial-hit+error; assert original error, nil response, no pending writes/deletes, no confirmation, simulation, signing, or broadcast. Count post-lookup RPC/channel validation if fixtures permit. Restore reads and prove recovery against the retained signature using the correct phase key; a normal healthy miss must still enter the existing full path. A successful helper-only test cannot detect a caller still checking only hit.

C. TS fresh lookup outage: reject with a sentinel Error and use rejects.toBe(sentinel), assert _verify/sign/send/confirm and pending Set/Delete were untouched, restore healthy reads, then settle the same payload successfully with exactly one send. A synchronous-throw variant is cheap useful coverage of the same boundary. Preserve existing healthy hit/miss controls.

D. TS actual overlap (essential): use per-call controlled promises, no sleeps or TTL advancement. Start A and hold its first get unresolved; this leaves A's newly acquired cache entry active. Start B on the same payload and make its get reject with a sentinel; assert the identical error and no work/pending mutations. Before releasing A, start C whose get resolves as a miss; C must return duplicate_settlement, with _verify/sign/send still at zero. Finally resolve A's lookup as a miss and await successful completion; verification/sign/send must each have happened only once. This demonstrates B cannot remove A's live entry, rather than merely inspecting a manually preseeded cache. Attach rejection assertions promptly and release all deferred promises in cleanup to avoid hanging tests.

Testing/claims boundary
Use deterministic mocks and existing fixtures; no live RPC or payment execution is necessary. The existing research proves erroneous settlement work/diagnostics and retry blockage, not an actual double charge. Storage recovery does not create a new automatic retry policy.
