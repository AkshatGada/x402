Findings

1. [P1] Capture and release admission when an application afterVerify hook aborts.
   Target: typescript/packages/mechanisms/evm/src/batch-settlement/server/scheme.ts:178
   Core invokes manual afterVerify hooks before the scheme adapter
   (core/src/server/x402ResourceServer.ts:1999,2011). An application hook that
   returns {abort:true} after successful facilitator verification triggers core
   cancellation immediately (core:1764), before managed.afterVerify has saved
   extra.pendingId. The scheme's settleOnCancel then sees no request context and
   skips the cancel settle. The caller sees verification rejection, while a
   normal next request to the channel must wait for the facilitator lease expiry.
   This is an application-policy hook on an otherwise valid payment, not a
   malformed or adversarial request.
   Actual TS SDK + actual pinned Go managed scheme evidence:
     verify response: {isValid:false,invalidReason:"application_policy_denied"}
     Go calls: verify=1, settle=0; held=true.
   Files: probe-lifecycle.mts, probe-lifecycle-async.log, lifecycle-evidence.json.
   The intended held=false assertion fails. The hook is async, matching the SDK
   hook signature. A narrow lifecycle/context fix is required; do not paper over
   it by fabricating or reusing a client-supplied reservation identity.
   The in-progress Python implementation already carries verify_result into its
   cancellation context for this ordering case; TS currently has no equivalent.

2. [P2] Release admission on a local settlement-enrichment failure.
   Target: typescript/packages/mechanisms/evm/src/batch-settlement/server/scheme.ts:120
   Managed onSettleFailure unconditionally drops the only pendingId context.
   When refund signing throws in managed.enrichSettlementPayload before the
   facilitator is called, this deletes the server's cleanup identity without
   canceling the admitted request. The reservation remains held until expiry.
   Reproduced with the actual TS client.refund method, TS resource server and Go
   managed scheme, using a local test signer that throws
   "simulated_signer_unavailable". Go calls: verify=1, settle=0; held=true.
   Files: probe-signer-failure.mts, probe-signer-failure.log,
   signer-failure-evidence.json. The intended held=false assertion fails.
   Cleanup should cover pre-facilitator failures without changing committed or
   non-terminal settlement outcomes. Retain context until cleanup/reconciliation
   is possible rather than forgetting an outstanding reservation.

3. [P2 design/correctness concern] Optional replica failures rewrite committed success.
   Target: typescript/packages/mechanisms/evm/src/batch-settlement/server/managed.ts:270
   A failed optional replica update throws AfterSettleAbortError, so core changes
   the authoritative successful receipt to success:false. The unchanged TS client
   response hook returns immediately on !success (client/hooks.ts:29) and does not
   adopt the committed watermark. A local replica outage can therefore make every
   paid request fail while the facilitator commits charges. This contradicts the
   managed pass-through contract and makes optional storage an availability
   dependency. The README acknowledges the behavior and the unit test explicitly
   asserts it; that is intentional behavior, not evidence that it is desirable.
   Recommendation: preserve facilitator success for replica I/O failure, report
   the mirror failure to operators, and test that the client adopts the committed
   receipt. Distinguish a malformed authoritative receipt from mirror persistence
   failure. This concern is separate from the two confirmed reservation leaks.

Positive review conclusions
- Explicit voucherManager configuration prevents accidental local managed
  admission; managed requirements use the advertised authorizer and delay, and
  require either a server refund key or delegatedRefund:true.
- Managed deposits/vouchers/refunds reach facilitator verification and settlement
  despite stale, empty, or restarted local stores. The worker guard is appropriate
  for the intentionally unported TS facilitator.
- pendingId/cancel are rejected on client verify input. Ordinary settlement and
  core's one settlement_pending retry carry the admitted pendingId unchanged.
- The client salt helper matches Go's bytes12 entropy + bytes20 refund key rule
  for raw and index salts; default server mode preserves raw salt behavior.
- Shared refund amount/claim/signing logic reduces duplication. Managed refunds
  never sign claim authority; the exact string nonce is used for consent even
  above 2^53. The unit independently verifies that typed-data signature.
- Corrective proofs for both cumulative mismatch reasons are copied from the
  facilitator rather than derived from the replica. Existing client signature
  validation remains responsible for adopting those proofs.
- The implementation does not add dependencies, storage/facilitator ports, legacy
  changes, misleading e2e catalog entries, or unrelated production edits.
