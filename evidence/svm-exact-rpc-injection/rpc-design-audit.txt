Minimal source recommendation
1. exact/client/scheme.ts: export ExactSvmClientConfig extending ClientSvmConfig (an interface or intersection type both work), with rpc?: Rpc<GetAccountInfoApi & GetLatestBlockhashApi>. Constructor uses this exact-specific config. Document injected RPC takes precedence over rpcUrl and must serve the payment network. Reuse normalizeNetwork before selection, then select config.rpc ?? createRpcClient(network, config.rpcUrl). Do not normalize the network string passed into the mint cache: preserving that original string preserves existing cache keys and alias behavior. An unconditional normalization followed by existing factory fallback adds only a cheap duplicate validation on the default path; conditional validation on the injected path is also acceptable if kept simple.
2. utils.ts: import Kit Rpc and GetLatestBlockhashApi types; change ONLY resolveBlockhash's rpc parameter from ReturnType<typeof createRpcClient> to Rpc<GetLatestBlockhashApi>. This reduces what the helper requires; all old default clients remain assignable. No body changes, casts or full RPC union are necessary. resolveOpenSlot and all other helpers remain untouched.
3. constants.ts: keep existing normalizeNetwork and supported CAIP-2 list. At the existing alias lookup guard, require an own property on V1_TO_V2_NETWORK_MAP. For ES2020 compatibility use Object.prototype.hasOwnProperty.call(V1_TO_V2_NETWORK_MAP, network), not Object.hasOwn. Minimal guard: if (!Object.prototype.hasOwnProperty.call(V1_TO_V2_NETWORK_MAP, network) || !caip2Network) { existing throw }. This is justified by preserving rejection of unsupported inputs in the injection path; no broader validation refactor is recommended.
4. exact/client/index.ts exports ExactSvmClientConfig; src/index.ts exports it directly from exact/client/scheme (or through the existing exact barrel if preferred). No need to add another file solely to relay one type. Both @x402/svm and @x402/svm/exact/client must expose it in generated declarations.
5. Focused actual-payload tests, concise README custom-transport/manual registration example, and @x402/svm minor changeset. Keep shared ClientSvmConfig, upto, batch, v1 and registration-helper types unchanged.

Why the type is correct
The installed Kit is 6.1.0. Its createSolanaRpcFromTransport returns RpcFromTransport<...>; an ordinary unbranded RpcTransport yields an unbranded Rpc. Requiring RpcDevnet|RpcTestnet|RpcMainnet/full factory ReturnType would unnecessarily demand cluster brands and additional methods. Kit Rpc<GetAccountInfoApi & GetLatestBlockhashApi> expresses precisely the exact-client operations. Existing fetchMint derives its input from fetchEncodedAccount; getCachedMintMetadata already derives its parameter from fetchMint. Neither requires a change.

Network findings and policy
- normalizeNetwork accepts all three supported CAIP-2 values and their existing solana, solana-devnet, solana-testnet aliases.
- Unknown Solana CAIP-2, foreign family and ordinary unknown names throw Unsupported SVM network today. Preserve this before mint fetching or blockhash resolution even when an injected RPC and supplied blockhash exist.
- The alias map is a regular object. Baseline normalizeNetwork('constructor'/'toString'/'__proto__') returns inherited nonstring values. The current createRpcClient switch rejects them afterward; a shortcut after normalization alone would newly allow them through. The own-property guard restores the same reject/accept contract without duplicating network constants. Their exact rejection message changes from factory Unsupported network to normalizer Unsupported SVM network; supported behavior and normal unknown errors remain unchanged. This was checked only as an offline ordinary unsupported-input contract, with no live probe or security claim.
- RPC cluster identity is the caller's responsibility, just as with fixed rpcUrl. Neither a Kit brand nor an endpoint URL proves the remote cluster. Do not add genesis hash, cluster discovery or validation RPC requests. README should show client.register(SOLANA_DEVNET_CAIP2, new ExactSvmScheme(signer, { rpc })) and advise separate scheme instances/registrations for different networks. Do not use a solana:* registration in the injection example.
- Do not canonicalize cache keys or introduce a client-routing map/factory. Both are unrelated behavior/API changes.

Required focused acceptance matrix
A. Real createSolanaRpcFromTransport backed by deterministic in-memory responses creates an actual exact v2 payment. Assert getAccountInfo and fallback getLatestBlockhash both hit the injected transport, the internal factory is never called, decoded transfer/payer/lifetime fields are correct and the payer signature verifies.
B. Provide both rpc and rpcUrl: same behavior proves precedence and excludes an unwanted default/fallback call. Can combine with A.
C. Omit rpc: supported custom rpcUrl and omitted rpcUrl still reach the existing factory with the same network/default semantics. Existing unit tests may cover part of this; avoid redundant parameter tables.
D. Supply a valid server blockhash: payload uses it and the injected transport receives no getLatestBlockhash. Still require network validation first. Retain existing malformed-hint fallback tests rather than duplicate their entire matrix.
E. Reuse scheme for same network/mint: mint read remains cached/coalesced and fallback blockhash still refreshes when required. Existing cache-specific tests cover coalescing/rejection eviction; ensure those run after the change. One sequential repeat through the injected client establishes it uses that cache.
F. Injected transport rejection propagates, without constructing or using the fallback client. A failed mint load followed by success can also confirm eviction if existing coverage does not already establish it.
G. Accepted CAIP-2 and alias inputs continue to work; unknown CAIP-2/name/foreign-family plus a representative inherited alias reject before any injected request or factory call. Existing normalizer tests can carry exhaustive alias cases, while injection tests focus on bypass prevention.
H. The real unbranded transport type is accepted by the implemented exported config through both public entrypoints; generated declarations build. No as any/as unknown casts to force compatibility. This is a useful compiler/build check, not a constructor-only runtime test pretending to verify behavior.

Preservation/risk boundaries
Mint metadata cache remains instance-local, keyed by original network+mint, with pending promise coalescing and rejection eviction. resolveBlockhash retains current supplied-hint semantics, including lastValidBlockHeight parsing/defaulting. Transaction composition, fee payer, memo, token program validation and signing remain unchanged. No transaction submission, rate-limit implementation, retries or production performance claims belong in this patch. Existing and targeted package checks remain necessary; this audit is design approval, not final implementation approval.
