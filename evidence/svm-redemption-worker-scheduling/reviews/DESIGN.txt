Behavior chosen
- Preserve setInterval cadence, first pass on first tick (no immediate new work on start).
- Skip automatic ticks while one automatic job is queued or running. Do not catch up missed historical ticks.
- Every explicit redeem() remains a distinct serialized pass with its own result/rejection, including manually queued passes.
- An automatic job already queued behind manual work is obsolete after stop(), and must not start a new runPass(). A pass already inside runPass() must finish normally; no transaction cancellation.
- stop(false) captures and waits the queue tail existing at invocation. stop(true) synchronously enqueues exactly one explicit final redeem and waits that promise. A later start/new manual request must not extend the earlier stop's captured boundary.
- start during a pending stop is permitted (existing API has no prohibition). New timer lifecycle cannot revive obsolete queued jobs from the old lifecycle, and completion of an old job cannot unlock a newer active automatic job. start twice while running remains a no-op. Every explicit flush request retains one pass; do not invent flush coalescing semantics.

Minimal implementation proposal, not yet written
Keep existing timer, running and passInFlight. Add private tickInFlight=false (covers queued + running automatic job across all lifecycles; never reset in start/stop) and private generation=0. Each successful start increments generation and captures its number in the timer callback. Every stop increments generation, sets running false, clears its timer synchronously before any await.

Factor existing redeem's queue operation into a private generic enqueue<T>(pass:()=>Promise<T>):Promise<T>, shared by public redeem and automatic tick. It chains onto passInFlight and catches only the stored tail, returning the pass's own promise unchanged. Existing manual error semantics remain. Keep current Promise<unknown> tail unless a strictly necessary type improvement arises; do not widen public interfaces.

Public redeem becomes return enqueue(()=>runPass()). Timer callback calls void tick(capturedGeneration). Private async tick:
  if (!running || generation !== capturedGeneration || tickInFlight) return;
  tickInFlight=true;
  try {
    await enqueue(async () => {
      if (!running || generation !== capturedGeneration) return;
      await runPass();
    });
  } catch (error) {
    config.onError?.(error);
  } finally {
    tickInFlight=false;
  }
Because the boolean is never reset on stop/start, no newer automatic job can enter while an old one still owns it. A queued old job releases the flag after its identity check skips it; a future current timer tick can then schedule. Guard release must survive rejected runPass. Throwing onError callback behavior need not be redesigned; flag still releases via finally.

stop captures either this.passInFlight (no flush) or this.redeem().catch(existing onError) (flush), then awaits only that captured promise. Do not reread mutable queue tail after awaiting a flush, as that could wait future-generation work. Update lifecycle JSDoc concisely; add one TS patch changeset. No README internals, new options, dependencies, backoff, timeouts or Go changes.
