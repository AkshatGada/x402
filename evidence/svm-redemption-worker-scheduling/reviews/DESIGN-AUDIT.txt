Why the state machine works
1. The automatic gate must be set synchronously before enqueue, cover queued as well as executing work, and be cleared only by that accepted tick's finally. With no start/stop reset, at most one accepted automatic job owns the gate across every lifecycle. Therefore an older job cannot finish after a newer automatic job has acquired the same gate: the newer job could not acquire it first. A generation-indexed gate map or separate promise ownership scheme would add unnecessary state.
2. Capture the generation in each start's timer closure, and compare it both at tick entry and inside the queued closure immediately before runPass. The entry check rejects callbacks from an old cleared timer; the execution check rejects an old job already queued behind manual work. A running boolean alone cannot distinguish stop/start from uninterrupted running. The generation must change synchronously on stop, before any await.
3. There is no await between the queued identity check and calling runPass, so JavaScript cannot slip a stop/start between them. Once runPass has begun, let it finish all existing claim/distribute/seal behavior. It may legitimately make later reads or settlement calls after stop was requested. This design cancels obsolete queued automatic passes, not an entered pass or a submitted transaction.
4. A shared private enqueue<T> is justified because public manual redemption and gated automatic work have different result types but must use one serial tail. Return the queued operation's own promise; absorb rejection only into the stored tail. Do not return the swallowed tail, suppress individual manual calls, or put manual redemption behind tickInFlight. Every manual call, including one made while stopped, remains a separate pass with its own outcome.
5. stop(false) must capture the existing swallowed tail once. stop(true) must synchronously append one explicit redeem and capture that call's handled promise once. Await only that captured boundary. Do not read this.passInFlight again after the await, and do not clear running/timer/generation after the await. Later manual calls or a restarted timer may begin before the old stop's continuation runs; they must not prolong or be clobbered by that old stop.

Microtask ordering does not invalidate these invariants. A completed queue job can settle its stored tail before tick's finally runs; the retained gate may conservatively skip another callback during those microtasks, but it cannot admit overlapping automatic jobs. Once finally releases the gate, the next current-generation interval callback can schedule. A stale queued closure can temporarily retain the gate behind old manual work after restart, but it eventually skips and releases; that is consistent with bounded skipped-tick semantics and does not create a new pass. An indefinitely blocked pass still blocks all later work, as it already did; adding timeouts or cancellation would be a separate policy.

Errors and explicit work
- A thrown/rejected runPass propagates to its manual caller, does not poison later queued calls, and lets an automatic tick report onError and release its gate in finally.
- A returned settlement_pending response is handled inside the existing runPass; it is not itself a rejected runPass. Do not conflate these two error paths in test claims.
- A throwing onError callback still releases the tick gate via finally. The ignored timer promise can then reject, as in the existing timer catch pattern. Do not broaden this fix into a new callback-error policy or claim to have solved unhandled user callback errors.
- Repeated explicit stop({flush:true}) calls each request one pass. A later stop can invalidate a newer timer lifecycle, but cannot cancel previously requested explicit flushes or manual calls.
- A stop promise resolving while a later generation is active is intentional under the chosen captured-boundary contract. Its JSDoc should say it waits for work already queued, plus the requested final pass; avoid saying the whole manager is idle when it resolves.

Required acceptance-test refinements
1. Add a compact repeated-flush case: while a pass is blocked, call stop({flush:true}) twice; release stages and prove exactly two additional serialized explicit passes execute. This protects the stated one-pass-per-request contract from accidental flush coalescing.
2. Add or parameterize a captured-boundary case for stop(false) with a later explicit redeem. Append that manual request after obtaining the stop promise, block its store stage, and prove the earlier stop resolves while the later request is still pending. The planned restart/flush case already exercises the more subtle stop(true) mutable-tail reread bug; keep it as well.

The existing plan otherwise covers the important counterexamples. Make its manual control assert the actual rejection object and independent successful results, rather than just three completions. Attach rejection observation immediately to avoid a false unhandled-rejection failure in the test. Use externally observable store/settler calls and deferred stages, not private-field assertions. In the queued-old-auto restart case, explicitly establish that the old automatic closure was queued behind manual work, then verify it adds no list calls after restart and that a subsequent current-generation tick runs and stays bounded. In the flush-boundary case, keep the final flush blocked long enough for the old automatic job to release its gate and a new-generation tick to queue behind the flush; otherwise the test can pass without exercising the bug.

Use the same focused test bytes and fixture schedules for baseline and fixed runs. Control cases should pass baseline, while backlog/obsolete-generation/boundary regressions should fail for the intended observable reason. Existing successful worker tests cover the payment path; there is no need to duplicate signing fixtures in this scheduler file. Ensure fake timers and blocked gates are cleaned up even on assertion failures so one expected baseline failure does not contaminate another case.
