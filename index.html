Scope and caveats

  • The official TS client sends one server-signed request per channel at a time. The parallel workers here model several clients or agent workers paying from the same channel; the spec lets server-mode handlers run concurrently and the server cannot rely on clients serializing. Their payloads are built with the SDK's signBatchAuthorization against the channel the official client opened.
  • Trigger. The control column shows main passing 24/24 with the SDK's in-memory stores under the same load. The failures need a store that re-runs the update callback after a write conflict (the shared SQLite store here uses the same optimistic loop as x402's EVM RedisChannelStorage) or whose write fails after the callback ran. Conflicts also happen inside one process, because the updater awaits voucher signing between its read and its compare-and-write; two replicas are not required.
  • Contracts. Go's ChannelStore says only “Update is atomic per channel”; it does not say whether the updater may run more than once. The TS interface says the updater runs with exclusive access and concurrent updates queue, so an optimistic TS store is outside that wording; for TS this change is hardening, plus the failed-write path, which is within either contract and is covered by unit tests in both SDKs.
  • Trade-off. With the fix, if operationStore.complete fails after the channel commit, the charge stays on the channel, the operation stays reserved (the request id is still fenced) and the request returns 402. On main the same failure leaves a completed operation with no charge. Neither is atomic; the PR states this.
  • What the harm is. On main the failed requests' bodies were withheld, so payers were not served for free and no funds were lost. The harm is merchant work done without a charge, an operation log that does not match the channel or the chain, and deposit held by reservations that block the payer's close until they expire.
  • Held reservations come from core not running onSettleFailure after a beforeSettle abort, so any abort holds its reservation until expiry (300 s). This PR removes these aborts, not that general behaviour. duplicate_settlement is the SDK's busy code returned to the refund.
  • Payout figures come from scanning the payTo token account for transactions that touch each channel. The redemption worker logged distribute failed: settlement_pending (slow devnet confirmation) in both arms before the distribute landed; this does not affect the comparison.
  • All runs disclosed. Two earlier baseline runs are not in the table: one stopped on a devnet RPC 429 before it saved results (its store showed the same 16 failures), and one completed 8/24 with the same failure before the error message was being recorded.
  • Devnet only, with a worthless test mint. The facilitator is a trimmed copy of the example; the harness itself is not part of the PR.
